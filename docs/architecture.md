# 初期構成と技術上の仮選択

## 今回の選択

**HTML/CSS/JavaScript＋Node.js標準機能のみ**で試作する。パッケージの追加取得なしに起動でき、認証基盤・DB・課金サービスを決める前に日報の入力と集計を検証できるため。

Node.js 24.xは今回の起動・テスト環境の指定。本番のフレームワーク・DB・ホスティングを決めたという意味ではない。npmで公開するパッケージではなく `private: true`。

| 層／パス | 責務 | 他の層との関係 |
| --- | --- | --- |
| `public/` | 日本語のHTML、モバイル幅のCSS | `src/ui/app.js`を読み込む |
| `src/ui/` | フォーム、タブ内状態、表示 | `domain`の検証・集計、`data`の架空マスタを使用 |
| `src/domain/` | 日報検証、同一ID更新、期間別の集計 | DOMやサーバー保存には依存しない |
| `src/data/` | 架空マスタ、デモ日報 | 実データや認証情報を置かない |
| `scripts/` | Node標準HTTPサーバー | `127.0.0.1`のみ、`public`と`src`の静的ファイルだけ配信 |
| `tests/` | 入力・連動・更新と配信範囲の検証 | Node標準テストランナーを使用 |
| `docs/` | 要件・未確定事項・画面・項目・手順 | 実装と一緒に更新 |

## データの流れ

画面入力から日報オブジェクトを作り、`validateReport`で検証し、`upsertReport`でタブ内の日報一覧へ反映する。画面表示時に`summarize`が日報を月で絞り、各台帳を計算する。

集計結果を別の台帳へ保存する仕組みはまだないため、修正前の値を持つ台帳との不整合を避けられる。正式な締め結果の保持は別途必要。

## 実用版への移行

1. Q01〜Q04の回答をもとに認証・API・DBを選ぶ。社員IDと認証IDを対応付ける。
2. API側で認証と権限を必ず検証する。UIの表示制限だけで保護しない。
3. 日報と子明細を一括で保存する。二重送信防止用ID、版番号による競合検知、変更履歴を設ける。
4. 日付・勤務区間・タイムゾーンはQ05・Q06に従って拡張する。今回の日付文字列を無条件でUTCの勤務日時に変換しない。
5. 適用期間付きの単価・計算規則、計算結果と元日報の版、締め後修正を設計する。
6. バックアップ・復元、監視、マスタ移行、iPhone実機、出力帳票を検証する。

将来の`api`・`db`フォルダは技術決定時に追加する。空フォルダや形だけのAPIを作って実装済みと見せない。

## 公開リポジトリと情報管理

リポジトリは公開されている。現在のコードには架空データのみを含める。`.gitignore`で環境変数ファイル・私的データ・バックアップ等を除外するが、これはアクセス制御ではない。コミット対象を毎回確認し、秘密情報が必要になってもソースへ直書きしない。

試作サーバーにはデータ登録API、ログイン、外部への通信、永続保存機能はない。公開ホスティング設定、公開URL、実データDB、外部アカウントは作成していない。
